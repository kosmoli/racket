1 弱盒子（Weak Boxes）🔗

一个 弱盒子 类似于普通盒子（参见 (part "boxes")），但当垃圾回收器（参见 (part "gc-model")）能够证明弱盒子的内容值仅通过弱引用可达时，弱盒子的内容将被替换为 #f。一个 weak reference 是指通过弱盒子的引用，通过弱哈希表中的键引用（参见 (part "hashtables")）、通过 ephemeron 的值（该值可被替换为 #f）（参见 Ephemerons），或通过 custodian（参见 (part "custodians")）的引用。

procedure

(make-weak-box v) → weak-box?

  v : any/c
返回一个初始包含 v 的新弱盒子。

procedure

(weak-box-value weak-box [gced-v]) → any/c

  weak-box : weak-box?
  gced-v : any/c = #f
返回 weak-box 中包含的值。若垃圾回收器已证明 weak-box 之前的内容值仅通过弱引用可达，则返回 gced-v（默认为 #f）。

procedure

(weak-box? v) → boolean?

  v : any/c
若 v 是弱盒子则返回 #t，否则返回 #f。

2 Ephemerons🔗

一个 ephemeron [Hayes97] 是 weak box（参见 弱盒子（Weak Boxes））的泛化。与仅包含一个值不同，ephemeron 持有两个值：一个被视为 ephemeron 的值，另一个则是 ephemeron 的键。与弱盒子中的值一样，ephemeron 中的值可能被替换为 #f，但当 键 不再可达时（除通过弱引用外），而不是值不再可达时。

只要 ephemeron 的值被保留，该引用就被视为非弱引用。然而，通过值对键的引用被特殊处理，即该引用不一定计入键的可达性。一个 weak box 可以看作 ephemeron 的特例，即键和值相同。

ephemeron 的一个特别常见的用途是将它们与弱哈希表（参见 (part "hashtables")）组合，以生成即使在值引用键时内存管理器也能回收键值对的映射；参见 make-ephemeron-hash。相关用途是只要任何值为可达的 impersonator 存在，就保留对该值的引用；参见 impersonator-ephemeron。

更精确地，

  • 当自动内存管理器能够证明 ephemeron 的键或 ephemeron 本身仅通过弱引用可达时（参见 弱盒子（Weak Boxes）），ephemeron 中的值被替换为 #f；且

  • 从 ephemeron 的值出发不可达的任何内容都不计入 ephemeron 键的可达性（无论是同一个 ephemeron 还是另一个），除非相同值通过非弱引用可达，或该值的 ephemeron 键通过非弱引用可达（有关弱引用的信息参见 弱盒子（Weak Boxes））。

procedure

(make-ephemeron key v) → ephemeron?

  key : any/c
  v : any/c
返回一个键为 key、初始值为 v 的新 ephemeron。

procedure

(ephemeron-value ephemeron [gced-v retain-v]) → any/c

  ephemeron : ephemeron?
  gced-v : any/c = #f
  retain-v : any/c = #f
返回 ephemeron 中包含的值。若垃圾回收器已证明 ephemeron 的键仅弱可达，则结果为 gced-v（默认为 #f）。

retain-v 参数被保留为可达，直到提取出 ephemeron 的值。例如，当 ephemeron 是通过弱 eq? 基映射从 key 获得，且 ephemeron 以 key 为键创建时，此参数很有用；在这种情况下，将 key 作为 retain-v 提供可确保 ephemeron 保留其值足够长时间以便被提取，即使 key 在其他方面不可达。

Changed in version 7.1.0.10: 添加了 retain-v 参数。

procedure

(ephemeron? v) → boolean?

  v : any/c
若 v 是 ephemeron 则返回 #t，否则返回 #f。

3 意愿与执行器（Wills and Executors）🔗

一个 will executor 管理一组值和一组关联的 will 过程 （亦称 finalizers）。每个值的 will 过程在该值被（垃圾回收器）证明为不可达时即可被执行，除非通过弱引用（参见 弱盒子（Weak Boxes））或作为其他 will executor 的注册者可达。will 对触发与不可达值关联的数据的操作很有用，例如当包含端口的对象不再使用时关闭嵌入在对象中的端口。

调用 will-execute 或 will-try-execute 过程会执行指定 will executor 中已就绪的 will。will executor 也是一个 synchronizable event，因此可使用 sync 或 sync/timeout 来检测 will executor 何时有就绪的 will。will 不会自动执行，因为某些程序需要控制以避免竞争条件。然而，程序可以创建一个线程，其唯一任务是为特定执行器执行 will。

若一个值在单个或多个 executor 中注册了多个 will，则 will 按注册的反向顺序被就绪。由于使 will 就绪会使值再次可达，因此必须执行 will 并再次证明值仅通过弱引用可达，才能就绪或执行另一个 will。然而，不同不可达值的 will 会同时就绪，无论这些值是否彼此可达。

will executor 的注册者被强引用保存，直到相应的 will 过程被执行。因此，若弱盒子（参见 弱盒子（Weak Boxes））的内容值注册了 will executor，弱盒子的内容不会更改为 #f，直到为该值执行了所有 will 且值再次被证明仅通过弱引用可达。

will executor 可用作 synchronizable event（参见 (part "sync")）。 当 will-execute 不会阻塞时，will executor 就是 ready for synchronization，即 the synchronization result of a will executor is the will executor itself。

以下示例展示了如何在不需要同步时运行清理操作。它只是作为另一个线程中注册的执行器就绪时运行它们。

Examples:
> (define an-executor (make-will-executor))
> (void
   (thread
    (λ ()
      (let loop ()
        (will-execute an-executor)
        (loop)))))
> (define (executor-proc v) (printf "a-box is now garbage\n"))
> (define a-box-to-track (box #f))
> (will-register an-executor a-box-to-track executor-proc)
> (collect-garbage)
> (set! a-box-to-track #f)
> (collect-garbage)

a-box is now garbage

procedure

(make-will-executor) → will-executor?

返回一个没有管理值的新 will executor。

procedure

(will-executor? v) → boolean?

  v : any/c
若 v 是 will executor 则返回 #t，否则返回 #f。

procedure

(will-register executor v proc) → void?

  executor : will-executor?
  v : any/c
  proc : (any/c . -> . any)
将值 v 注册到 will executor executor 中的 will 过程 proc。当 v 被证明为不可达时，过程 proc 即可通过 will-execute 或 will-try-execute 以 v 作为其参数被调用。proc 参数被强引用保存，直到 will 过程被执行。

procedure

(will-execute executor) → any

  executor : will-executor?
调用注册到执行器 executor 的单个 "不可达" 值的 will 过程。will 过程返回的值是 will-execute 调用的结果。如果没有 will 立即可供执行，will-execute 会阻塞直到有就绪的 will。

procedure

(will-try-execute executor [v]) → any

  executor : any/c
  v : any/c = #f
如果 will 立即可供执行，则类似 will-execute。否则返回 v。

Changed in version 6.90.0.4: 添加了 v 参数。

4 垃圾回收🔗

在 Racket 启动前设置 PLTDISABLEGC 环境变量（为任意值）可禁用 garbage collection。设置 PLT_INCREMENTAL_GC 环境变量为以 1、y 或 Y 开头的值以请求 Racket 的 3m 实现始终使用增量模式，但在带有定期任务的程序中调用 (collect-garbage 'incremental) 通常是请求增量模式的更好机制。设置 PLT_INCREMENTAL_GC 环境变量为以 0、n 或 N 开头的值可禁用增量模式请求（在所有 Racket 实现中）。

每次垃圾回收都会在 'debug 级别、以 'GC 为主题记录一条消息（参见 (part "logging")）。在 Racket 的 CS 和 3m 实现中，"主要" 回收也会在 'debug 级别、以 'GC:major 为主题记录。在 Racket 的 CS 和 3m 实现中，消息的数据部分是一个 gc-info prefab 结构体实例，包含以下 10 个字段，但 Racket 的未来版本可能使用带有额外字段的 gc-info prefab 结构体：

(struct gc-info (mode pre-amount pre-admin-amount code-amount
                      post-amount post-admin-amount
                      start-process-time end-process-time
                      start-time end-time)
  #:prefab)

  • mode 字段是符号 'major、 'minor 或 'incremental；'major 表示检查所有内存的回收， 'minor 表示主要只检查最近分配的回收， 'incremental 表示执行额外工作以推进下一次主要回收的次要回收。

    Changed in version 6.3.0.7: 将第一个字段从布尔值 （#t 表示 'major，#f 表示 'minor） 更改为模式符号。

  • pre-amount 字段报告开始 garbage collection 时 （即不包括子 place 的内存使用量）以字节为单位的位置本地内存使用量。 通过 make-phantom-bytes 注册的额外字节也被包含在内。

  • pre-admin-amount 是包含垃圾回收器开销的更大数字， 例如已映射但未使用的内存页面空间。

  • code-amount 字段报告生成的原生代码的额外内存使用量 （垃圾回收前后相同，因为它通过 finalization 释放）。

  • post-amount 和 post-admin-amount 字段 对应于 pre-amount 和 pre-admin-amount，但它们在垃圾回收之后。在典型配置中， post-amount 与 pre-amount 之间的差异 贡献于 post-admin-amount，因为被回收的页面倾向于保留储备， 以备预期将被再次需要（但如果多次回收都未需要这些页面，则它们会被释放）。

  • start-process-time 和 end-process-time 字段报告垃圾回收开始和结束时（在 current-process-milliseconds 意义上）的处理器时间。时间差是回收消耗的处理器时间。

  • start-time 和 end-time 字段报告 垃圾回收开始和结束时的实际时间（在 current-inexact-milliseconds 意义上）。时间差是垃圾回收消耗的实际时间。

所记录消息的文本格式可能会改变。 目前，在指示 place 和回收模式的前缀之后，文本格式为

‹used›(‹admin›)[‹code›]; free ‹reclaimed›(‹adjust›) ‹elapsed› @ ‹timestamp›

‹used›

 

垃圾回收前正在使用的可回收内存

‹admin›

 

用于管理可回收内存的额外内存

‹code›

 

生成的机器代码使用的额外内存

‹reclaimed›

 

垃圾回收回收的可回收内存

‹adjust›

 

行政内存变化减去 ‹reclaimed› 的相反数

‹elapsed›

 

执行垃圾回收所用处理器时间

‹timestamp›

 

垃圾回收启动以来的处理器时间

Changed in version 6.3.0.7: 添加了 PLT_INCREMENTAL_GC。
Changed in version 7.6.0.9: 为主题 'GC:major 添加了主要回收日志记录。

procedure

(collect-garbage [request]) → void?

  request : (or/c 'major 'minor 'incremental) = 'major
请求一次即时 garbage collection 或请求一个垃圾回收模式，取决于 request：

  • 'major —— 强制进行 "主要" 回收， 检查所有内存。某些实际上不可达的数据可能 不会被收集，因为回收器无法证明它 不可达。

    collect-garbage 此模式提供了对回收时机的一些控制，但 显然即使从不调用此过程，垃圾也会被收集——除非通过设置 PLTDISABLEGC 禁用了垃圾回收。

  • 'minor —— 请求 "次要" 回收，主要只检查最近的分配。如果 次要回收不被支持（例如 (system-type 'gc) 返回 'cgc）或如果下一次回收必须是主要回收，则不执行任何回收。更一般地， 由 (collect-garbage 'minor) 触发的次要回收不会导致 主要回收比原本发生时更早。

  • 'incremental —— 不请求即时回收，但请求未来额外努力以避免 主要回收，即使这需要每次次要回收做更多工作以增量执行主要回收的工作。此增量模式请求在下一次主要回收时过期。

    增量模式的意图是显著减少主要回收导致的暂停时间，但增量模式可能意味着 更长的次要回收时间和更高的内存使用。目前， 增量模式仅对 Racket 的 CS 和 3m 实现有意义；它在其他 Racket 实现中无效。

    如果 PLT_INCREMENTAL_GC 环境变量的值在启动时以 0、n 或 N 开头，则增量模式请求将被忽略。

Changed in version 6.3: 添加了 request 参数。
Changed in version 6.3.0.2: 添加了 'incremental 模式。
Changed in version 7.7.0.4: 为 Racket CS 添加了 'incremental 效果。

procedure

(current-memory-use [mode]) → exact-nonnegative-integer?

  mode : (or/c #f 'cumulative 'peak custodian?) = #f
返回内存使用信息：

  • 若 mode 为 #f（默认值），结果为从任意 custodian 可达的字节数的估计值。

  • 若 mode 为 'cumulative，返回自启动以来分配的字节总数的估计值， 包括已被垃圾回收回收的字节。

  • 若 mode 为 'peak，返回 Racket 进程启动以来在任何垃圾回收之前已分配字节数的最大值。

  • 若 mode 是 custodian，返回从 mode 可达数据占用的内存字节数的估计值。 此估计值由最后一次垃圾回收计算，如果未发生回收（或自给定 custodian 创建以来未发生回收），则可能为 0。 current-memory-use 函数本身 不 执行回收；在调用前执行回收通常会减小结果（或如果尚未发生回收则从 0 增加）。

    当 Racket 编译时未启用内存记账支持，对于任何单个 custodian，估计值与 mode 为 #f 时相同（即所有内存）。另请参见 custodian-memory-accounting-available?。

另请参见 vector-set-performance-stats!。

Changed in version 6.6.0.3: 添加了 'cumulative 模式。
Changed in version 8.10.0.3: 添加了 'peak 模式。

procedure

(dump-memory-stats v ...) → any

  v : any/c
将内存使用信息转储到低级错误端口或控制台。

v 参数的各种组合可以控制转储中的信息。可用的信息取决于你的 Racket 构建；检查特定构建的转储末尾以查看是否提供额外信息；否则所有 v 都会被忽略。

5 幻字节串（Phantom Byte Strings）🔗

一个 phantom byte string 是一个小的 Racket 值，被 Racket 内存管理器视为具有任意大小，该大小在创建 phantom byte string 时或通过 set-phantom-bytes! 更改时指定。

phantom byte string 作为对 Racket 内存管理器的提示，表示内存是在进程内分配的，但通过单独的分配器，例如通过 ffi/unsafe 访问的外部库。此提示用于触发 garbage collections 或计算 current-memory-use 的结果。

procedure

(phantom-bytes? v) → boolean?

  v : any/c
若 v 是 phantom byte string 则返回 #t，否则返回 #f。

procedure

(make-phantom-bytes k) → phantom-bytes?

  k : exact-nonnegative-integer?
创建一个 phantom byte string，被 Racket 内存管理器视为大小为 k 字节。对于足够大的 k，会引发 exn:fail:out-of-memory exception is raised——要么因为大小大得离谱，要么因为已通过 custodian-limit-memory 安装了内存限制。

procedure

(set-phantom-bytes! phantom-bstr k) → phantom-bytes?

  phantom-bstr : phantom-bytes?
  k : exact-nonnegative-integer?
调整 phantom byte string 被 Racket 内存管理器视为的大小。

例如，若 phantom-bstr 表示的内存通过外部库释放，则 (set-phantom-bytes! phantom-bstr 0) 可以反映内存使用的变化。

当 k 大于 phantom-bstr 的当前大小时，此函数可能引发 exn:fail:out-of-memory，类似于 make-phantom-bytes。
