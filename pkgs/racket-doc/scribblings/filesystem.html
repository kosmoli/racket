1 定位路径🔗

procedure

(find-system-path kind) → path?

  kind : symbol?
返回由 kind 指定的标准类型路径的机器特定路径， kind 必须是以下之一：

  • 'home-dir — 当前 用户主目录。

    在所有平台上，如果 PLTUSERHOME 环境变量被定义为 完整 路径， 则该路径被用作用户主目录。

    在 Unix 和 Mac OS 上，当 PLTUSERHOME 不适用时， 用户主目录通过展开路径 "~" 来确定， 展开时首先检查 HOME 环境变量。如果未定义， 则按顺序查询 USER 和 LOGNAME 环境变量以找到用户名， 然后查询系统文件以定位用户主目录。

    在 Windows 上，当 PLTUSERHOME 不适用时， 用户主目录是由 Windows 注册表确定的用户特定配置文件目录。 如果注册表由于某种原因无法提供目录，则使用 USERPROFILE 环境变量的值， 只要它引用存在的目录。如果 USERPROFILE 也失败， 则目录由 HOMEDRIVE 和 HOMEPATH 环境变量指定。 如果这些环境变量未定义，或者指示的目录仍不存在， 则使用包含当前可执行文件的目录作为主目录。

  • 'pref-dir — 用于存储当前用户偏好的标准目录。 偏好目录可能不存在。

    在 Unix 上，偏好目录通常是指定路径的 "racket" 子目录， 该路径由 XDG_CONFIG_HOME 指定，或者如果 XDG_CONFIG_HOME 未设置为绝对路径或设置了 PLTUSERHOME，则为 用户主目录 中的 ".config/racket"。无论哪种方式，如果该目录不存在但 用户主目录 中存在 ".racket" 目录，则该目录是偏好目录。

    在 Windows 上，如果由 PLTUSERHOME 确定，则偏好目录是 用户主目录 中的 "Racket"，否则是 Windows 注册表指定的用户应用程序数据文件夹； 应用程序数据文件夹通常是用户配置文件目录中的 "Application Data"。

    在 Mac OS 上，偏好目录是 用户主目录 中的 "Library/Preferences"。

  • 'pref-file — 包含以符号为键的偏好值关联列表的文件。 文件的目录路径始终与为 'pref-dir 返回的结果匹配。 在 Unix 和 Windows 上，文件名为 "racket-prefs.rktd"， 在 Mac OS 上为 "org.racket-lang.prefs.rktd"。 文件的目录可能不存在。另参见 get-preference。

  • 'temp-dir — 用于存储临时文件的标准目录。 在 Unix and Mac OS 上，这是由 TMPDIR 环境变量指定的目录（如果已定义）， 否则是 "/var/tmp"、"/usr/tmp" 和 "/tmp" 中第一个存在的路径。 在 Windows 上，结果是由 TMP 或 TEMP 环境变量指定的目录 （如果已定义），否则是当前目录。

  • 'init-dir — 包含 Racket 可执行文件使用的初始化文件的目录。

    在 Unix 上，初始化目录与为 'pref-dir 返回的结果相同—— 除非该目录不存在且 用户主目录 中存在 ".racketrc" 文件， 在这种情况下主目录是初始化目录。

    在 Windows 上，初始化目录与 用户主目录 相同。

    在 Mac OS 上，初始化目录是 用户主目录 中的 "Library/Racket"—— 除非那里不存在 "racketrc.rktl" 且主目录中确实存在 ".racketrc" 文件， 在这种情况下主目录是初始化目录。

  • 'init-file — Racket 可执行文件在启动时加载的文件。 路径的目录部分与为 'init-dir 返回的路径相同。

    在 Windows 上，名称的文件部分是 "racketrc.rktl"。

    在 Unix 和 Mac OS 上，名称的文件部分是 "racketrc.rktl"—— 除非为 'init-dir 返回的路径是 用户主目录， 在这种情况下名称的文件部分是 ".racketrc"。

  • 'config-dir — 安装配置的目录。 此目录由 PLTCONFIGDIR 环境变量指定， 可以通过 --config 或 -G 命令行标志覆盖。 如果未指定环境变量或标志，或者值不是合法的路径名， 则此目录默认为相对于当前可执行文件的 "etc" 目录。 如果 (find-system-path 'config-dir) 的结果是相对路径， 则它相对于当前可执行文件。 该目录可能不存在。

  • 'host-config-dir — 类似于 'config-dir，但在选择跨平台构建模式时 （通过 racket 的 -C 或 --cross 参数；参见 (part "mz-cmdline")）， 结果引用当前系统安装的目录，而不是目标系统的目录。

  • 'addon-dir — 用于用户特定 Racket 配置、包和扩展的目录。 此目录由 PLTADDONDIR 环境变量指定， 可以通过 --addon 或 -A 命令行标志覆盖。 如果未指定环境变量或标志，或者值不是合法的路径名， 则此目录默认为平台特定的位置。该目录可能不存在。

    在 Unix 上，默认值通常是指定路径的 "racket" 子目录， 该路径由 XDG_DATA_HOME 指定，或者如果 XDG_CONFIG_HOME 未设置为绝对路径或设置了 PLTUSERHOME，则为 用户主目录 中的 ".local/share/racket"。如果该目录不存在但用户主目录中存在 ".racket" 目录， 则 ".racket" 目录路径是默认值。

    在 Windows 上，默认值与 'pref-dir 目录相同。

    在 Mac OS 上，默认值是 用户主目录 中的 "Library/Racket"。

  • 'host-addon-dir — 类似于 'addon-dir，但在选择跨平台构建模式时 （通过 racket 的 -C 或 --cross 参数；参见 (part "mz-cmdline")）， 结果引用当前系统安装的目录，而不是目标系统的目录。

    Added in version 8.17.0.2.

  • 'cache-dir — 用于存储用户特定缓存的目录。 该目录可能不存在。

    在 Unix 上，缓存目录通常是指定路径的 "racket" 子目录， 该路径由 XDG_CACHE_HOME 指定，或者如果 XDG_CACHE_HOME 未设置为绝对路径或设置了 PLTUSERHOME，则为 用户主目录 中的 ".cache/racket"。如果该目录不存在但主目录中存在 ".racket" 目录， 则 ".racket" 目录是缓存目录。

    在 Windows 上，缓存目录与为 'addon-dir 返回的结果相同。

    在 Mac OS 上，缓存目录是 用户主目录 中的 "Library/Caches/Racket"。

  • 'doc-dir — 用于存储当前用户文档的标准目录。 在 Unix 上，它是 用户主目录。在 Windows 上，如果由 PLTUSERHOME 确定， 则它是 用户主目录，否则是 Windows 注册表指定的用户文档文件夹； 文档文件夹通常是用户主目录中的 "My Documents"。 在 Mac OS 上，它是 用户主目录 中的 "Documents" 目录。

  • 'desk-dir — 当前用户桌面的目录。 在 Unix 上，它是 用户主目录。在 Windows 上，如果由 PLTUSERHOME 确定， 则它是 用户主目录，否则是 Windows 注册表指定的用户桌面文件夹； 桌面文件夹通常是用户主目录中的 "Desktop"。在 Mac OS 上， 它是 用户主目录 中的 "Desktop"。

  • 'sys-dir — 包含 Windows 操作系统的目录。 在 Unix and Mac OS 上，结果是 "/"。

  • 'exec-file — 操作系统为当前调用提供的 Racket 可执行文件路径。 对于某些操作系统，路径可以是相对的。

    对于 GRacket，可执行文件路径是 GRacket 可执行文件的名称。

  • 'run-file — 当前可执行文件的路径； 这可能与 'exec-file 的结果不同，因为通过 --name 或 -N 命令行标志向 Racket（或 GRacket）可执行文件提供了备用路径， 或者因为嵌入的可执行文件安装了备用路径。特别是由 make-racket-launcher 创建的“启动器”脚本将此路径设置为脚本的路径。

  • 'collects-dir — 主库集合的路径（参见 (part "collects")）。 如果此路径是相对的，则它相对于 (find-system-path 'exec-file) 报告的可执行文件—— 尽管后者可能是软链接或相对于用户的可执行文件搜索路径， 因此两个结果应与 find-executable-path 结合使用。 'collects-dir 路径通常嵌入在 Racket 可执行文件中， 但可以通过 --collects 或 -X 命令行标志覆盖。

  • 'host-collects-dir — 类似于 'collects-dir，但在选择跨平台构建模式时 （通过 racket 的 -C 或 --cross 参数；参见 (part "mz-cmdline")）， 结果引用当前系统安装的目录，而不是目标系统的目录。 在跨平台构建模式下，集合文件通常从目标系统的安装中读取， 但某些任务需要相对于主库集合路径配置的当前系统目录 （例如保存外部库的目录）。

  • 'orig-dir — 启动时的当前目录， 在将 (find-system-path 'exec-file) 或 (find-system-path 'run-file) 的相对路径结果转换为完整路径时有用。

Changed in version 6.0.0.3: 添加了 PLTUSERHOME。
Changed in version 6.9.0.1: 添加了 'host-config-dir 和 'host-collects-dir。
Changed in version 7.8.0.9: 添加了 'cache-dir，并更改 为在 Unix 上优先使用 XDG 目录， 以前的路径作为回退， 并对 Mac OS 进行类似调整。

procedure

(path-list-string->path-list str 
  default-path-list) 
 → (listof (or/c path? 'same))
  str : (or/c string? bytes?)
  default-path-list : (listof (or/c path? 'same))
解析包含路径列表的字符串或字节字符串，并返回路径列表。 在 Unix and Mac OS 上，路径列表字符串中的路径由 : 分隔； 在 Windows 上，路径由 ; 分隔，并且字符串中的所有 " 被丢弃。 每当路径列表包含空路径时，列表 default-path-list 被拼接到返回的路径列表中。 str 中不形成有效路径的部分不包含在返回的列表中。 给定的 str 不得包含 nul 字符或 nul 字节。

Changed in version 8.0.0.10: 更改为允许 default-path-list 中使用 'same。

procedure

(find-executable-path program    
  [related    
  deepest?]) → (or/c path? #f)
  program : path-string?
  related : (or/c path-string? #f) = #f
  deepest? : any/c = #f
查找可执行文件 program 的路径，如果找不到路径则返回 #f。

在 Windows 上，如果未找到 program 且它没有文件扩展名， 则搜索重新开始，将 ".exe" 添加到 program， 仅当带有 ".exe" 的路径也找不到时结果才为 #f。 如果仅找到带扩展名的 program，则结果包含扩展名 ".exe"。

如果 related 不是 #f，则它必须是相对路径字符串， 并且为 program 找到的路径必须使得文件或目录 related 存在于与可执行文件相同的目录中。然后结果是找到的 related 的完整路径， 而不是可执行文件的路径。

此过程由 Racket 可执行文件用于查找标准库集合目录（参见 (part "collects")）。 在这种情况下，program 是用于启动 Racket 的名称， related 是 "collects"。使用 related 参数是因为， 在 Unix and Mac OS 上，program 可能涉及一系列软链接； 在这种情况下，related 确定链中哪个链接是相关的。

如果 related 不是 #f，则当 find-executable-path 未找到是另一个文件路径链接的 program 时， 搜索可以继续沿着链接的目标进行。进一步检查链接，直到找到 related 或到达链接链的末尾。如果 deepest? 是 #f（默认值）， 则结果对应于找到 related 的链接链中的第一个路径 （实际上不探索进一步的链接）；否则，结果对应于找到 related 的链中的最后一个链接。

如果 program 是无路径的名称， find-executable-path 获取 PATH 环境变量的值； 如果此环境变量已定义，find-executable-path 尝试 PATH 中的每个路径 作为 program 的前缀，使用上述用于包含路径的 program 的搜索算法。 如果 PATH 环境变量未定义，program 将与当前目录前缀 并用于上述搜索算法。（在 Windows 上，当前目录始终是 PATH 中的第一个隐式项， 因此 find-executable-path 在 Windows 上首先检查当前目录。）

Changed in version 8.1.0.7: 在 Windows 上添加了使用 ".exe" 的搜索。

2 文件🔗

procedure

(file-exists? path) → boolean?

  path : path-string?
如果文件（不是目录）path 存在则返回 #t， 否则返回 #f。

在 Windows 上，file-exists? 对所有特殊文件名变体报告 #t （例如 "LPT1"、"x:/baddir/LPT1"）。

procedure

(link-exists? path) → boolean?

  path : path-string?
如果链接 path 存在则返回 #t， 否则返回 #f。

谓词 file-exists? 或 directory-exists? 在链接或一系列链接的最终目标上工作，而 link-exists? 仅跟随链接以解析 path 的基本部分（即路径中除最后一个名称外的所有内容）。

此过程从不引发 exn:fail:filesystem 异常。

在 Windows 上，link-exists? 对符号链接和结点都报告 #t。

Changed in version 6.0.1.12: 在 Windows 上添加了对链接的支持。

procedure

(file-or-directory-type path [must-exist?])

 → (or/c 'file 'directory 'link 'directory-link #f)
  path : path-string?
  must-exist? : any/c = #f
报告 path 是指文件、目录、链接还是目录链接（在 Windows 的情况下； 另参见 make-file-or-directory-link），假设 path 可以被访问。

如果 path 无法被访问，当 must-exist? 为 #f 时结果为 #f， 否则 exn:fail:filesystem exception is raised。

Added in version 7.8.0.5.

procedure

(delete-file path) → void?

  path : path-string?
删除路径为 path 的文件（如果存在），否则 exn:fail:filesystem exception is raised。 如果 path 是链接，则删除链接而不是链接的目标。

在 Windows 上，如果初始删除文件的尝试因权限错误而失败， 且 current-force-delete-permissions 的值为真， 则 delete-file 尝试更改文件的权限（以允许写入）然后删除文件； 权限更改后跟删除是非原子序列，如果删除失败则不尝试恢复权限更改。

在 Windows 上，delete-file 可以删除符号链接，但不能删除结点。 使用 delete-directory 删除结点。

在 Windows 上，请注意，如果文件在仍被某个进程使用时（例如，后台搜索索引器）被删除， 则文件的内容最终会消失，但文件的名称仍被占用，直到文件不再被使用。 只要名称仍被占用，尝试打开、删除或替换文件将触发权限错误（而不是文件存在错误）。 避免此陷阱的常见技巧是在删除文件之前将其移动到生成的临时名称。 另参见 delete-directory/files。

Changed in version 6.1.1.7: 更改 Windows 行为以使用 current-force-delete-permissions。

procedure

(rename-file-or-directory old    
  new    
  [exists-ok?]) → void?
  old : path-string?
  new : path-string?
  exists-ok? : any/c = #f
将路径为 old 的文件或目录（如果存在）重命名为路径 new。 如果文件或目录未成功重命名，则 exn:fail:filesystem exception is raised。

此过程可用于将文件/目录移动到不同的目录（在同一文件系统上）， 以及在目录内重命名文件/目录。除非 exists-ok? 作为真值提供， new 不能引用现有的文件或目录，但在 Unix 和 Mac OS 上， 检查与重命名操作不是原子的。即使 exists-ok? 为真， 当 old 是目录时，new 不能引用现有文件，反之亦然。

如果 new 存在并被替换，在 Unix 和 Mac OS 上替换是原子的， 但在 Windows 上不保证是原子的。此外，如果 new 存在并被任何进程打开进行读取或写入， 则尝试替换它通常在 Windows 上会失败。另参见 call-with-atomic-output-file。

如果 old 是链接，则重命名链接而不是链接的目标， 并且对于替换任何现有 new 都算作文件。

在 Windows 上，请注意，如果目录中有任何文件处于打开状态，则目录无法重命名。 如果搜索索引器在后台运行（如在默认 Windows 配置中），此约束特别成问题。 可能的解决方法是组合 copy-directory/files 和 delete-directory/files， 因为后者可以处理打开的文件，尽管该序列显然不是原子的并且会临时复制文件。

procedure

(file-or-directory-modify-seconds path    
  [secs-n]) → exact-integer?
  path : path-string?
  secs-n : #f = #f
(file-or-directory-modify-seconds path    
  secs-n) → void?
  path : path-string?
  secs-n : exact-integer?
(file-or-directory-modify-seconds path    
  [secs-n    
  fail-thunk]) → any
  path : path-string?
  secs-n : (or/c exact-integer? #f) = #f
  fail-thunk : (-> any)

返回 文件或目录的最后修改日期，以 纪元 以来的秒数表示 （另参见 (part "time")），当 secs-n 未提供或为 #f 时。

对于 Windows 上的 FAT 文件系统，目录没有修改日期。 因此，为目录返回创建日期，为文件返回修改日期。

如果提供了 secs-n 且不为 #f，则将 path 的访问和修改时间设置为给定时间。

出错时（例如，如果文件不存在），则调用 fail-thunk（通过尾部调用） 以产生 file-or-directory-modify-seconds 调用的结果。 如果未提供 fail-thunk，则引发 exn:fail:filesystem 错误。

procedure

(file-or-directory-permissions path [mode])

 → (listof (or/c 'read 'write 'execute))
  path : path-string?
  mode : #f = #f
(file-or-directory-permissions path mode) → (integer-in 0 65535)
  path : path-string?
  mode : 'bits
(file-or-directory-permissions path mode) → void
  path : path-string?
  mode : (integer-in 0 65535)
当给定一个参数或 #f 作为第二个参数时， 返回包含 'read、'write 和/或 'execute 的列表，以指示当前用户和组对给定文件或目录路径的权限。 在 Unix and Mac OS 上，检查的是当前有效用户而不是实际用户的权限。

如果提供 'bits 作为第二个参数，则结果是文件或目录属性 （主要是权限）的平台特定整数编码，结果独立于当前用户和组。 编码的最低九位是可移植的，反映文件或目录所有者、 文件目录组成员或其他用户的权限：

  • #o400 : 所有者具有读权限

  • #o200 : 所有者具有写权限

  • #o100 : 所有者具有执行权限

  • #o040 : 组具有读权限

  • #o020 : 组具有写权限

  • #o010 : 组具有执行权限

  • #o004 : 其他用户具有读权限

  • #o002 : 其他用户具有写权限

  • #o001 : 其他用户具有执行权限

4 检测文件系统更改🔗

许多操作系统提供文件系统更改通知， 这些通知在 Racket 中通过 文件系统更改事件 反映。

(filesystem-change-evt? v) → boolean?

  v : any/c

procedure

(filesystem-change-evt path [failure-thunk])

 → (or/c filesystem-change-evt? any)
  path : path-string?
  failure-thunk : (or/c (-> any) #f) = #f
创建一个 文件系统更改事件，它是一个 可同步事件， 在 path 更改后变为 准备好同步：

  • 如果 path 引用文件，当文件的内容或属性更改或文件被删除时， 事件变为 准备好同步。

  • 如果 path 引用目录，当目录中添加、重命名或删除文件或子目录时， 事件变为 准备好同步。

如果事件传递给 filesystem-change-evt-cancel， 事件也会变为 准备好同步。

最后，取决于操作系统可用信息的精度， 事件可能在其他情况下变为 准备好同步。 例如，在 Windows 上，当文件所在目录中的任何文件更改时， 文件的事件变为就绪。

文件系统更改事件 变为 准备好同步 后， 它将保持 准备好同步 状态。事件的 同步结果 是事件本身。

如果当前平台不支持文件系统更改通知， 则当 failure-thunk 未提供为过程时 exn:fail:unsupported exception is raised， 或者如果提供了 failure-thunk，则在尾部位置调用它。 同样，如果创建事件时出现任何操作系统错误（例如不存在的文件）， 则 exn:fail:filesystem exception is raised 或调用 failure-thunk。

创建文件系统更改事件会在操作系统级别分配资源。 资源最迟在事件同步且 准备好同步 时释放， 当事件通过 filesystem-change-evt-cancel 取消时释放， 或者当垃圾收集器确定文件系统更改事件不可达时释放。 另参见 system-type 的 'fs-change 模式。

文件系统更改事件在创建时置于 当前监管者 的管理之下。 如果 监管者 关闭，filesystem-change-evt-cancel 将应用于事件。

Changed in version 7.3.0.8: 允许 failure-thunk 为 #f。

5 声明运行时需要的路径🔗

 (require racket/runtime-path) package: base
The bindings documented in this section are provided by the racket/runtime-path library, not racket/base or racket.

racket/runtime-path 库提供了用于在运行时访问文件和目录的形式， 使用通常相对于封闭源文件的路径。与使用 collection-path 不同， define-runtime-path 将每个运行时路径暴露给可执行文件和分发创建器等工具， 以便运行时需要的文件和目录随分发一起携带。

除了下面描述的绑定之外，racket/runtime-path 在 阶段级别 1 提供 #%datum，因为字符串常量通常用作 define-runtime-path 的编译时表达式。

syntax

(define-runtime-path id maybe-runtime?-id expr)

 
maybe-runtime?-id = 
  | #:runtime?-id runtime?-id
将 expr 同时用作编译时（即 阶段 1）表达式和运行时（即 阶段 0）表达式。 在任一上下文中，expr 应产生路径、表示路径的字符串、 形式为 (list 'lib str ...+) 的列表，或形式为 (list 'so str) 或 (list 'so str vers) 的列表。 如果提供了 runtime?-id，则它在 expr 的上下文中绑定， 对于 expr 的编译时实例为 #f，对于运行时为 #t。

对于运行时，id 绑定到基于 expr 结果的路径。 路径通常通过取 expr 的相对路径结果并将其添加到封闭文件的路径来计算 （计算方式如下所述）。然而，可执行文件创建器等工具也可以安排 （通过与 racket/runtime-path 协作）在生成的可执行文件中替换不同的基本路径。 如果 expr 产生绝对路径，通常直接返回， 但同样可能被可执行文件创建器替换。在所有情况下， 可执行文件创建器保留给定 包 内所有路径的相对位置 （将任何包外的路径视为在一起）。 当 expr 产生相对或绝对路径时，绑定到 id 的路径始终是绝对路径。

如果 expr 产生形式为 (list 'lib str ...+) 的列表， 绑定到 id 的值是绝对路径。该路径引用类似于将值用作 模块路径 的基于集合的文件。

如果 expr 产生形式为 (list 'so str) 或 (list 'so str vers) 的列表， 绑定到 id 的值可以是 str 或绝对路径； 当在 Racket 特定的共享对象库目录（由 get-lib-search-dirs 确定）中搜索定位路径时， 它是绝对路径。通过这种方式，专门为 Racket 安装的共享对象库随分发一起携带。 搜索按顺序尝试每个目录；在目录内，搜索首先尝试直接使用 str， 然后尝试添加 vers 指定的每个版本——默认为 '(#f)—— 以及平台特定的共享库扩展——由 (system-type 'so-suffix) 产生。 vers 可以是字符串，也可以是字符串和 #f 的列表。

如果 expr 产生形式为 (list 'share str) 的列表， 绑定到 id 的值可以是 str 或绝对路径； 当在 find-user-share-dir 和 find-share-dir 报告的目录中 （按该顺序）搜索定位路径时，它是绝对路径。 通过这种方式，安装在 Racket 的 "share" 目录中的文件随分发一起携带。

如果 expr 产生形式为 (list 'module module-path var-ref) 或 (list 'so str (list str-or-false ...)) 的列表， 绑定到 id 的值是 模块路径索引， 其中 module-path 被视为相对于作为 变量引用 var-ref 的家的模块 （如果是相对的），其中如果 module-path 是绝对的， var-ref 可以是 #f。在可执行文件中， 相应的模块随其所有依赖项一起携带。

对于编译时，expr 结果由可执行文件创建器使用—— 而不是包含模块编译时的结果。相反，expr 作为编译时表达式 （在 begin-for-syntax 的意义上）保留在模块中。 后来，在创建可执行文件时，模块的编译时部分再次执行， expr 的结果是要与可执行文件包含的文件或目录。 额外编译时执行的原因是 expr 的结果可能是平台相关的， 因此结果不应存储在模块的（平台无关的）字节码形式中； 然而，创建可执行文件时的平台与运行时的平台相同。 请注意，expr 在运行时仍然被求值；因此， 避免使用像 collection-path 这样依赖于源安装的过程， 而使用相对路径和像 (list 'lib str ...+) 这样的形式。

如果某些路径仅在某些平台而非其他平台上需要， 请使用 define-runtime-path-list 并在不需要路径的平台上让 expr 产生空列表。

请注意，如果 expr 在创建可执行文件时产生目录的路径， 目录的完整内容（包括任何子目录）将与可执行文件或最终分发一起包含。

还要注意，define-runtime-path 在 阶段级别 0 以外的阶段中 不能正确与可执行文件创建器协作。为了解决该限制， 将 define-runtime-path 放在单独的模块中—— 也许是由 module 创建的 子模块——然后导出定义， 然后可以在任何阶段级别 require 包含该定义的模块。 在 阶段级别 0 以外的阶段使用 define-runtime-path 会在展开时记录警告。

define-runtime-path 的封闭路径按以下方式从 define-runtime-path 语法形式确定：

  • 如果形式根据 syntax-source-module 具有源模块， 则源位置通过将原始表达式保留为语法对象来确定， 在运行时（再次使用 syntax-source-module）提取其源模块路径， 然后解析生成的模块路径索引。请注意，syntax-source-module 基于语法对象的 词法信息，而不是其源位置。

  • 如果表达式没有源模块， 则使用与形式关联的 syntax-source 位置， 如果是字符串或路径。

  • 如果没有源模块可用，且 syntax-source 不产生路径， 则使用 current-load-relative-directory（如果不是 #f）。 最后，如果所有其他方法都失败，则使用 current-directory。

在后两种情况下，路径通常以（平台特定的）字节形式保留， 但如果封闭路径对应于 collection-file-path 的结果， 则路径记录为相对于相应模块路径。

Changed in version 6.0.1.6 of package base: 仅在包内保留相对路径。
Changed in version 7.5.0.7: 添加了对 expr 中 'share 的支持。

procedure

(fold-files proc    
  init-val    
  [start-path    
  follow-links?]) → any
  proc : 
(or/c (path? (or/c 'file 'dir 'link) any/c
        . -> . any/c)
      (path? (or/c 'file 'dir 'link) any/c
        . -> . (values any/c any/c)))
  init-val : any/c
  start-path : (or/c path-string? #f) = #f
  follow-links? : any/c = #t
从 start-path 开始遍历文件系统， 对每个发现的文件、目录和链接调用 proc。 如果 start-path 是 #f，则遍历从 (current-directory) 开始。

proc 过程对每个文件、目录或链接使用三个参数调用：

  • 如果 start-path 是 #f，则第一个参数是相对于当前目录的路径名字符串。 否则，第一个参数是以 start-path 开头的路径名。因此， 为 start-path 提供 (current-directory) 与提供 #f 不同， 因为在后一种情况下 proc 接收相对路径，而在前一种情况下接收完整路径。 另一个区别是当 start-path 是 #f 时， proc 不会为当前目录调用。

  • 第二个参数是符号，'file、'dir 或 'link。 当 follow-links? 为 #f 时，第二个参数可以是 'link， 在这种情况下文件系统遍历不跟随链接。如果 follow-links? 为 #t， 则 proc 仅在遇到悬空符号链接（不解析为现有文件或目录的链接）时 才会将 'link 作为第二个参数接收。

  • 第三个参数是累积结果。对于 proc 的第一次调用， 第三个参数是 init-val。对于 proc 的第二次调用（如果有）， 第三次调用的第三个参数是第一次调用的结果，依此类推。 proc 的最后一次调用的结果是 fold-files 的结果。

proc 参数的使用方式类似于 foldl 的过程参数， 其结果用作新的累积结果。对于目录的情况（当第二个参数是 'dir 时）有一个例外： 在这种情况下，过程可以返回两个值，第二个值指示是否应包含给定目录的递归扫描。 如果返回单个值，则扫描目录。对于文件或链接的情况 （当第二个参数是 'file 或 'link 时），允许第二个值但被忽略。

如果提供了 start-path 但这样的路径不存在，或者路径在扫描过程中消失， 则引发异常。

Windows 阻止程序删除或替换打开的文件，但允许重命名打开的文件。 因此，在 Windows 上，call-with-atomic-output-file 默认创建第二个临时文件 extra-tmp-file，将 file 重命名为 extra-tmp-file， 将由 proc 写入的临时文件重命名为 file，最后删除 extra-tmp-file。 然而，由于该过程不是原子的，如果提供了 rename-fail-handler， 则使用 rename-file-or-directory， 因为移动的源和目标将在同一目录中，rename-file-or-directory 有原子的机会； 尝试重命名文件时的任何文件系统异常都会发送到 rename-fail-handler， 它可以重新 raise 异常或仅返回以重试，可能在延迟之后。 除了文件系统异常，rename-fail-handler 过程还接收要移动到 path 的临时文件路径。 rename-fail-handler 参数仅在 Windows 上使用。

Changed in version 7.1.0.6 of package base: 添加了 #:rename-fail-handler 参数。

从 (find-system-path 'pref-file) 指定的文件中提取偏好值， 或者如果提供了 filename 且不为 #f，则从 filename 中提取。 在前一种情况下，如果偏好文件不存在，get-preferences 尝试读取 旧偏好文件，然后读取配置目录中的 "racket-prefs.rktd" 文件 （由 find-config-dir 报告）。如果这些文件都不存在，偏好集为空。

偏好文件应包含使用默认参数设置写入的符号-值列表的列表。 以 racket:、mzscheme:、mred: 和 plt: 开头的键 （任何字母大小写）保留给 Racket 实现者使用。 如果偏好文件不包含符号-值列表的列表，则通过 log-error 记录错误并调用 failure-thunk。

get-preference 的结果是如果 name 存在于关联列表中则返回关联的值， 否则返回调用 failure-thunk 的结果。

偏好设置在 get-preference 调用之间（弱）缓存， 使用 (path->complete-path filename) 作为缓存键。 如果 flush-mode 作为 #f 提供，则使用缓存而不是重新查询偏好文件。 如果 flush-mode 作为 'timestamp（默认值）提供， 则仅当文件的时间戳与上次读取文件的时间相同时才使用缓存。否则，重新查询文件。

在 preferences-lock-file-mode 返回 'file-lock 的平台上， 当 use-lock? 为真时，偏好文件读取由锁保护；多个读取者可以共享锁，但写入者独占获取锁。 如果偏好文件因锁不可用而无法读取，则在锁文件的路径上调用 lock-there； 如果 lock-there 是 #f，则引发异常。 默认的 lock-there 处理程序重试约 5 次（每次尝试之间的延迟增加）， 然后尝试 timeout-lock-there，默认的 timeout-lock-there 触发异常。

另参见 put-preferences。对于更精细的偏好系统，参见 preferences:get。

  • Mac OS：(build-path (find-system-path 'pref-dir) "org.plt-scheme.prefs.ss")

  • Unix：(expand-user-path "~/.plt-scheme/plt-prefs.ss")

(put-preferences names    
  vals    
  [locked-proc    
  filename]) → void?
  names : (listof symbol?)
  vals : list?
  locked-proc : (or/c #f (path? . -> . any)) = #f
  filename : (or/c #f path-string?) = #f
安装一组偏好值并将所有当前值写入由 (find-system-path 'pref-file) 指定的偏好文件， 或者如果提供了 filename 且不为 #f，则写入 filename。

names 参数提供偏好名称，vals 必须与 names 长度相同。 vals 的每个元素必须是内置数据类型的实例， 其 write 输出是 read 可读的（即在写入偏好时将 print-unreadable 参数设置为 #f）。

更新前从偏好文件读取当前偏好值，并在文件读取之前开始持有写锁，直到偏好文件更新后释放。 锁通过在与偏好文件相同的目录中存在文件来实现； 参见 preferences-lock-file-mode 了解更多信息。 如果偏好文件的目录不存在，则创建它。

如果写锁已被持有，则 locked-proc 使用单个参数调用：锁文件的路径。 默认的 locked-proc（当 locked-proc 参数为 #f 时使用）报告错误； 替代的 thunk 可能等待一段时间然后重试，或者让用户选择删除锁文件 （如果先前的更新尝试遇到灾难并且锁是通过锁文件的存在实现的）。

如果 filename 是 #f 或未提供，且偏好文件不存在， 则从 "defaults" 集合（如果有）读取的值将写入未在 names 中提及的偏好。

procedure

(preferences-lock-file-mode) → (or/c 'exists 'file-lock)

报告当前平台上用于实现偏好文件锁定的锁文件使用方式。

'exists 模式目前用于除 Windows 外的所有平台。 在 'exists 模式下，锁文件的存在表示持有写锁，读取者不需要锁 （因为偏好文件通过 rename-file-or-directory 原子更新）。

'file-lock 模式目前用于 Windows。在 'file-lock 模式下， 锁文件上的共享和独占锁（在 port-try-file-lock? 的意义上） 反映偏好文件内容的读取者和写入者锁。 （偏好文件本身未锁定，因为锁定会干扰通过 rename-file-or-directory 替换文件。）

  filename

创建一个适合用作 get-preference 的 #:lock-there 参数的过程， 其中 name、failure-thunk、flush-mode 和 filename 都传递给 get-preference 由结果过程重试偏好查找。

在调用 get-preference 之前，结果过程使用 (sleep delay) 暂停。 然后，如果 (* 2 delay) 小于 max-delay， 结果过程调用 make-handle-get-preference-locked 生成新的重试过程 传递给 get-preference，但 delay 为 (* 2 delay)。 如果 (* 2 delay) 不小于 max-delay， 则使用给定的 lock-there 调用 get-preference。

procedure

(call-with-file-lock/timeout filename    
  kind    
  thunk    
  failure-thunk    
  [#:lock-file lock-file    
  #:delay delay    
  #:max-delay max-delay]) → any
  filename : (or/c path-string? #f)
  kind : (or/c 'shared 'exclusive)
  thunk : (-> any)
  failure-thunk : (-> any)
  lock-file : (or/c #f path-string?) = #f
  delay : (and/c real? (not/c negative?)) = 0.01
  max-delay : (and/c real? (not/c negative?)) = 0.2
获取文件名 lock-file 的锁，然后调用 thunk。 filename 参数指定仅当 lock-file 为 #f 时用于生成锁文件名的文件路径前缀。 具体来说，当 lock-file 为 #f 时， call-with-file-lock/timeout 使用 make-lock-file-name 构建锁文件名。 如果锁文件尚不存在，则创建它；请注意，锁文件不会被 call-with-file-lock/timeout 删除。

当 thunk 返回时， call-with-file-lock/timeout 释放锁，返回 thunk 的结果。 call-with-file-lock/timeout 函数将在 delay 秒后重试， 并以指数退避继续重试，直到延迟达到 max-delay。 如果 call-with-file-lock/timeout 无法获取锁， 则在尾部位置调用 failure-thunk。kind 参数指定锁是 'shared 还是 'exclusive，在 port-try-file-lock? 的意义上。

Examples:
> (call-with-file-lock/timeout filename 'exclusive
    (lambda () (printf "File is locked\n"))
    (lambda () (printf "Failed to obtain lock for file\n")))

File is locked

> (call-with-file-lock/timeout #f 'exclusive
    (lambda ()
      (call-with-file-lock/timeout filename 'shared
        (lambda () (printf "Shouldn't get here\n"))
        (lambda () (printf "Failed to obtain lock for file\n"))))
    (lambda () (printf "Shouldn't get here either\n"))
    #:lock-file (make-lock-file-name filename))
