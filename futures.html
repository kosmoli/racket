Futures🔗

(part ("(lib scribblings/guide/guide.scrbl)" "effective-futures")) in (part ("(lib scribblings/guide/guide.scrbl)" "top")) introduces futures.

 (require racket/future) package: base
The bindings documented in this section are provided by the racket/future and racket libraries, but not racket/base.

通过 future 实现的并行支持在 CS 实现中通常对所有平台启用。 在 BC 实现中，并行支持默认在 Windows、Linux x86/x86_64 和 Mac OS x86/x86_64 上启用。要为其他平台启用 Racket BC 的并行支持， 在 configure 时使用 --enable-futures。

racket/future 中的 future 和 touch function 提供对硬件和操作系统支持的并行性的访问。与 thread 为任意计算提供并发而不提供并行不同，future 提供并行性。一个 future 并行执行其工作（在并行支持可用的情况下），直到它检测到尝试执行无法安全并行运行的操作。类似地，future 的工作如果以某种方式依赖于当前 continuation（例如引发异常），就会被暂停。会暂停 future 的操作称为 blocking 操作。Future 的暂停计算会在 touch 应用于该 future 时恢复。

Future 的“安全”并行执行意味着系统提供的所有操作都能强制执行 contract 并按照文档所述产生结果。“安全”并不排除对程序中可见的 mutable 数据的并发访问。例如，future 中的计算可能使用 set! 修改共享变量，在这种情况下，对该变量的并发赋值在其他 future 和 thread 中可见。此外，关于效应可见性和顺序的保证由操作系统和硬件决定——它们很少支持，例如为基于 thread 的并发提供的顺序一致性保证；另见 (part "memory-order")。显然安全的系统操作可能在内部实现上无法并行运行；见 (part ("(lib scribblings/guide/guide.scrbl)" "top")) 中的 (part ("(lib scribblings/guide/guide.scrbl)" "effective-futures")) 以了解更多讨论和 future-visualizer 的介绍，用于理解系统操作的行为。

如果允许创建 thread 运行的所有 custodian 都被关闭，future 就永远不会并行运行。但这样的 future 仍然可以通过 touch 调用执行。

1 创建与 Touching Futures🔗

procedure

(future thunk) → future?

  thunk : (-> any)

procedure

(touch f) → any

  f : future?
future function 返回一个封装了 thunk 的 future 值。touch function 强制求值给定 future 内的 thunk，返回 thunk 产生的值。在 touch 强制求值一个 thunk 后，结果值会被 future 保留以替代 thunk，对该 future 的后续 touch 调用返回这些值。

在对给定 future 的 future 调用和 touch 之间，给定的 thunk 可能会与其他计算一起被推测性地并行执行，如上所述。

Example:
> (let ([f (future (lambda () (+ 1 2)))])
    (list (+ 3 4) (touch f)))

'(7 3)

procedure

(futures-enabled?) → boolean?

返回当前 Racket 配置中是否启用了对 future 的并行支持。

procedure

(current-future) → (or/c #f future?)

返回其 thunk 执行是当前 continuation 的 future 描述符；也就是说，如果返回了 future 描述符 f，(touch f) 将产生当前 continuation 的结果。如果 future thunk 本身使用 touch，future-thunk 的执行可以是嵌套的，在这种情况下返回正在立即执行的 future 的描述符。如果当前 continuation 不返回到任何 future 的 touch，结果为 #f。

procedure

(future? v) → boolean?

  v : any/c
Returns #t if v is a future value, #f otherwise.

procedure

(would-be-future thunk) → future?

  thunk : (-> any)
返回一个永远不会并行运行的 future，但在执行 future thunk 期间会一致地记录所有潜在的“不安全”操作（即干扰并行执行的操作）。

对于普通 future，某些情况可能阻止记录不安全操作。例如，当使用 debug 级别日志执行时，

(touch (future (lambda ()
                 (printf "hello1")
                 (printf "hello2")
                 (printf "hello3"))))

可能会为每次 printf 调用记录一条消息，共三条。然而，如果 touch 在 future 有机会开始并行运行之前执行，future thunk 会以与普通 thunk 相同的方式求值，不会记录任何不安全操作。用 would-be-future 替换 future 可确保所有三个 printf 调用都被记录。

procedure

(processor-count) → exact-positive-integer?

返回当前机器上可用的并行计算单元数量（例如处理器或核心）。

这与 racket/place 中可用的 binding 相同。

syntax

(for/async (for-clause ...) body-or-break ... body)

syntax

(for*/async (for-clause ...) body-or-break ... body)

Like for 和 for*，但 body 的每次迭代在单独的 future 中执行，future 可以按任意顺序被 touch。

2 Future Semaphore🔗

procedure

(make-fsemaphore init) → fsemaphore?

  init : exact-nonnegative-integer?
创建并返回一个新的 future semaphore，计数器初始设置为 init。

Future semaphore 类似于普通的 semaphore，但 future-semaphore 操作可以安全地并行执行（用于同步并行计算）。相比之下，普通 semaphore 上的操作执行不安全，它们因此阻止计算继续并行执行。

警惕尝试使用 fsemaphore 来实现 lock。Future 可能与其他 future 并发并行运行，但未被 Racket thread 需求的 future 可以随时被暂停——比如在它获取 lock 之后和释放 lock 之前。如果必须在 future 之间共享 mutable 数据，无锁数据结构通常是更好的选择。

procedure

(fsemaphore? v) → boolean?

  v : any/c
Returns #t if v is an future semaphore value, #f otherwise.

procedure

(fsemaphore-post fsema) → void?

  fsema : fsemaphore?
递增 future semaphore 的内部计数器并返回 #<void>。

procedure

(fsemaphore-wait fsema) → void?

  fsema : fsemaphore?
阻塞直到 fsema 的内部计数器非零。当计数器非零时，它会被递减，fsemaphore-wait 返回 #<void>。

procedure

(fsemaphore-try-wait? fsema) → boolean?

  fsema : fsemaphore?
Like fsemaphore-wait，但 fsemaphore-try-wait? 不会阻塞执行。如果 fsema 的内部计数器为零，fsemaphore-try-wait? 立即返回 #f 而不递减计数器。如果 fsema 的计数器为正，它会被递减并返回 #t。

procedure

(fsemaphore-count fsema) → exact-nonnegative-integer?

  fsema : fsemaphore?
返回 fsema 的当前内部计数器值。

3 Future 性能日志🔗

Racket traces 使用 logging（参见 (part "logging")）广泛地报告关于 futures 如何被求值的信息。Logging 输出对调试使用 futures 的程序的性能很有用。

尽管文本日志输出可以直接查看（或通过代码中 trace-futures 检索）， 但使用 future-visualizer 提供的图形化 profiler 工具更容易。

Future events 的日志主题是 'future。除了 string message 之外， 每个为 future 记录的事件都有一个数据值，该数据值是一个 future-event prefab 结构体的实例：

(struct future-event (future-id proc-id action time prim-name user-data)
  #:prefab)

future-id 字段是一个用于标识 future 的精确整数， 或在 action 是 'missing 时为 #f。 future-id 字段对关联记录的事件特别有用。

proc-id 字段是一个用于标识 parallel process 的精确非负整数。 进程 0 是主 Racket 进程，除了 future thunks 之外的所有表达式都在 该进程中求值。

time 字段是一个表示时间的 inexact 数，表示方式与 current-inexact-milliseconds 相同。

action 字段是一个 symbol：

  • 'create：创建了一个 future。

  • 'complete：future 的 thunk 成功完成，使得 touch 会立即为该 future 生成一个值。

  • 'start-work 和 'end-work：特定进程开始和停止处理 特定 future。

  • 'start-0-work：类似于 'start-work，但用于因某种 结构原因而无法在进程 0 以外的进程中开始的 future thunk（例如，thunk 需要大量本地存储才能开始）。

  • 'start-overflow-work：类似于 'start-work，其中 future thunk 的工作之前由于内部 stack overflow 而停止。

  • 'sync：阻塞（进程 0 除外）或发起交付（进程 0），用于 future thunk 求值中的"不安全"操作；该操作必须在进程 0 中运行。

  • 'block：类似于 'sync，但用于必须延迟到 future 被 touch 时才能进行的求值部分，因为求值可能依赖于当前 continuation。

  • 'touch（从不在进程 0 中）：类似于 'sync 或 'block，但用于 future thunk 内的 touch 操作。

  • 'overflow（从不在进程 0 中）：类似于 'sync 或 'block，但用于进程在求值 future thunk 时遇到内部栈溢出的情况。

  • 'result 或 'abort：等待或处理 'sync、 'block 或 'touch，以值或错误分别结束。

  • 'suspend（从不在进程 0 中）：'sync、'block 或 'touch 阻塞的进程放弃对 future 的求值；某个其他进程可能 稍后会接手该 future。

  • 'touch-pause 和 'touch-resume（仅在进程 0 中）： 在 touch 中等待一个 thunk 在另一个进程中被求值的 future。

  • 'missing：一个或多个进程的事件在可以报告之前由于内部 buffer 限制而丢失，而 time-id 字段报告丢失事件的时间的上限；这种 类型的事件很少见。

假设没有 'missing 事件，那么 'start-work、 'start-0-work、'start-overflow-work 总是与 'end-work 成对出现； 'sync、'block 和 'touch 总是与 'result、'abort 或 'suspend 成对出现；而 'touch-pause 总是与 'touch-resume 成对出现。

在进程 0 中，某些事件对可以嵌套在其他事件对内： 'sync、'block 或 'touch 与 'result 或 'abort；'touch-pause 与 'touch-resume；'start-work 与 'end-work。

在进程 0 中，当处理不安全操作时会生成 'block。这种类型的事件在 unsafe-op-name 字段中包含一个 symbol，该 symbol 是操作的名称。 在所有其他情况下，此字段包含 #f。

prim-name 字段始终为 #f，除非事件发生在进程 0 上， 且其 action 是 'block 或 'sync。如果满足 这些条件，prim-name 将包含一个 symbol，表示要求 future 与 runtime thread 同步的 Racket primitive 的名称。

user-data 字段根据 action 和 prim-name 字段 的不同，可能采用多种不同的值：

  • 'touch 在进程 0 上：包含正在被 touch 的 future 的 整数 ID。

  • 'sync 且 prim-name 是 '|allocate memory|： 所请求分配的字节大小。

  • 'sync 且 prim-name 是 'jit_on_demand： runtime thread 正在为 future future-id 执行 JIT 编译。 该字段包含被 JIT 编译的函数的名称（作为 symbol）。

  • 'create：创建了一个新的 future。该字段包含新创建 的 future 的整数 ID。
